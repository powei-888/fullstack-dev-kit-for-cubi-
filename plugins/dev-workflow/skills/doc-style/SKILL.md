# 技術文件寫作風格

目標：讀者看一次就懂，而且沒有第二種讀法。文件放在哪裡、要有哪些 metadata 依專案的文件規範；本檔只管句子怎麼寫。使用者指定其他風格時以使用者為準。

## 句子

- 一句只講一件事。超過 35 字就檢查能不能拆開。
- 用主動語態，寫出誰做什麼：「系統寫入 log」，不寫「log 被寫入」。
- 動詞直接用，不加「進行」「予以」「加以」：「驗證 token」，不寫「進行 token 的驗證」。
- 能用肯定句就不用否定句：「只接受 UTF-8」，不寫「不接受非 UTF-8」。
- 刪除填充語：「值得注意的是」「基本上」「總而言之」「如前所述」。

## 步驟

- 一步一個動作，用祈使句，依序編號。
- 條件放在動作前面：「若 token 過期，重新登入」。
- 警告放在它所保護的步驟之前。
- 每個步驟寫明預期結果或驗證方式。

## 用詞

- 一詞一義：同一個概念全文只用一個詞，不為了避免重複而換同義詞。
- 專有名詞第一次出現時先定義，之後固定使用。
- 不用模糊詞：「適當」「相關」「必要時」「盡量」「視情況」。改寫成具體條件、數值或對象。
- 強度用固定詞：必須（不做會出錯）、禁止、建議（可不做但有風險）、可以（選項）。
- 數字用阿拉伯數字並帶單位：「30 秒」「3 次」。
- 指令、路徑、檔名、欄位名、版本號用 code 格式。
- 使用台灣慣用詞與全形標點；英文術語與識別字保持原樣。

## 結構

- 結論先行：第一段說明這份文件解決什麼問題。
- 一段一主題，不超過 5 句。
- 並列 3 項以上改用列表；比較多個屬性改用表格。
- 標題寫內容，不寫口號。

## 現況與計畫分開

- 已經實作的行為用現在式；尚未實作的明確標示為計畫，不寫「系統會」。
- 不確定的內容標註「待確認」，不用猜測補齊。

## 交稿前檢查

- 有沒有超過 35 字且含兩個以上動作的句子？
- 同一概念是否出現兩種以上說法？
- 有沒有無法驗證的模糊詞？
- 步驟是否一步一動作，且警告在步驟之前？
