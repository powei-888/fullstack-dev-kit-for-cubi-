# 測試撰寫原則

測試放置位置、命名風格與執行指令依專案現況，不依本檔。先看專案既有測試怎麼寫，再套用下列原則。

## 原則

1. **測試放在行為所在的那一層**：業務判斷測 service，查詢與資料對應測資料存取層，HTTP 輸入輸出與權限測 controller 或整合測試。
2. **只替換邊界依賴**：資料庫、外部服務、queue、檔案系統、時鐘。不要 mock 被測物件自己的內部方法。
3. **一個測試一個行為**：成功、失敗、無權限、邊界值分開寫。測試名稱直接說出行為與預期結果。
4. **斷言對外可觀察的結果**：回傳值、拋出的錯誤、對邊界依賴的呼叫參數。不斷言私有狀態。
5. **預期值不從被測實作 import**：需要雜湊或計算結果時在測試內重算。否則實作改壞時測試跟著變，什麼都擋不住。
6. **優先鎖住「錯了也不會報錯」的行為**：權限被放寬、欄位漏查、狀態沒寫回、稽核沒記錄。在測試旁註解改壞的後果。
7. **測試之間不共用可變狀態**：每個測試自行準備資料與 mock；整合測試清除自己建立的資料並關閉連線。
8. **不為了通過測試而改 production 行為**：不放寬邏輯、不調高門檻、不把略過的測試算成功。
9. **測試資料只用合成資料**：不放真實使用者資料、token 或密碼。

## 單元測試驗不到的行為

交易與回滾、連線隔離、資料庫 migration、中介層與 guard 的執行順序、queue 投遞。這些要用整合測試或實際啟動驗證。沒有驗證時在回報中明講，不可因為單元測試全過就宣稱功能正常。

## 完成檢查

- 新增或修改的測試單獨執行會通過，與其他測試一起執行也會通過。
- 修 bug 時，補的測試在修復前會失敗。
- 只讀測試名稱就能知道這段程式的預期行為。
